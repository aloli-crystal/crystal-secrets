== v0.5.0 — 2026-05-10

=== Ajouté — `secrets env` pour `.env.age` (ferme la fuite `.env` en prod)

Un fichier `.env` sur un serveur de production est un vecteur de
fuite récurrent. v0.5.0 livre la pièce manquante pour ne jamais
avoir de `.env` en clair sur disque en production : un verbe qui
opère sur les fichiers `.env.age` chiffrés au roster courant, et
une forme `exec` qui déchiffre en mémoire et fait
`Process.exec` sur la commande cible avec les paires `KEY=VALUE`
injectées dans son environnement.

Surface CLI :

* `secrets env encrypt FILE.env [-o FILE.env.age]` — écrit le
  ciphertext mode 0600, chiffré avec `Recipients.encryption_keys`.
* `secrets env decrypt FILE.env.age [-o FILE.env]` — utile en dev ;
  émet un warning que le plaintext est sur disque (la prod doit
  préférer `exec`).
* `secrets env exec FILE.env.age -- CMD [ARGS...]` — déchiffre en
  mémoire, parse les paires `KEY=VALUE`, les insère dans
  l'environnement, puis `Process.exec` sur la cible. Aucun
  plaintext n'est jamais écrit sur disque. L'image du processus
  appelant est remplacée — il n'y a pas de « ligne après exec ».
* `secrets env edit FILE.env.age` — même UX que `secrets edit`
  mais avec `.env` comme suffixe d'éditeur.

`Secrets::Env.parse` est un parser `.env` minimal : commentaires,
lignes vides, préfixe `export` optionnel, valeurs entre quotes
simples ou doubles. Pas de multi-ligne, pas d'expansion
`${VAR}`, pas de substitution de commande — un coffre est un
keystore plat, pas un script d'init shell.

=== Ajouté — backend identité-fichier (chemin Linux/FreeBSD minimal)

`MasterKey.read` retombe désormais sur un fichier d'identité
mode 0600 dans `${XDG_CONFIG_HOME:-~/.config}/secrets/identity`
si aucune entrée Keychain n'est accessible. Sur macOS l'ordre est
Keychain → fichier (un fichier d'identité placé manuellement est
une issue de secours valide en SSH sur un Mac headless). Sur toute
autre plateforme, le fichier est la seule option.

`MasterKey.generate!` et `.install!` écrivent dans le backend
adéquat sélectionné à la compilation via `{% if flag?(:darwin) %}`.

C'est intentionnellement minimal — les backends Linux Secret
Service, Windows Credential Manager et FreeBSD passphrase restent
hors scope. Le backend fichier est le contrat dont tout serveur
a besoin pour faire tourner `secrets env exec` dès aujourd'hui.

=== Refactor

* `MasterKey.exists?` introduit (vrai si une clé est accessible par
  *n'importe quel* backend) — remplace les appels directs
  `KeychainMacOS.exists?` dans `generate!`.
* `MasterKey.read` ne mentionne plus Keychain dans son message
  d'erreur — fonctionne identiquement sur tous les backends.

=== Tests

* `spec/env_spec.cr` — 10 examples couvrant les cas limites du
  parser `.env` (commentaires, vides, quotes, quotes
  dépareillées, préfixe `export`, ligne sans `=`, signe `=` dans
  la valeur, espaces autour de la clé, round-trip complet
  encrypt → decrypt via age).
* Total : 55 examples, 0 failures.

== v0.4.0 — 2026-05-10

=== Ajouté — coffres multi-recipients (lot 2 de la roadmap README)

Les coffres peuvent désormais être chiffrés pour une *liste* de
clés publiques au lieu d'un recipient unique. N'importe laquelle
des identités listées peut ensuite déchiffrer — c'est le cas
partage en équipe.

`Vault.encrypt` gagne un overload `Array(String)` :

  Secrets::Vault.encrypt(plaintext, ["age1alice...", "age1bob...", "age1...soi..."])

L'overload string unique est conservé en wrapper fin pour
compatibilité ascendante. `Vault.decrypt` est inchangé — age gère
nativement les fichiers multi-recipients ; toute identité qui
correspond peut déchiffrer.

=== Ajouté — module `Secrets::Recipients` + CLI `secrets recipients`

Le roster vit dans
`${XDG_CONFIG_HOME:-~/.config}/secrets/recipients.toml`, mode 0644
(les clés publiques ne sont pas secrètes), versionable, au format
TOML :

  [recipients]
  alice = "age1alice..."
  bob   = "age1bob..."

La clé maîtresse de l'opérateur est ajoutée automatiquement par
`Recipients.encryption_keys` — impossible de se verrouiller hors
de son propre coffre par un typo dans le roster.

Surface CLI :

* `secrets recipients add NAME AGE_KEY` (alias `a`) — ajout/mise à jour.
* `secrets recipients remove NAME` (alias `rm`, `r`) — suppression.
* `secrets recipients list` (alias `ls`, `l`) — affiche name → key.
* `secrets recipients help` — aide de la sous-commande.

Après chaque `add` / `remove`, l'opérateur doit lancer
`secrets rotation -n VAULT` sur chaque coffre qui doit refléter le
nouveau roster — `rotation` re-chiffre avec
`Recipients.encryption_keys` (introduit en v0.3.0, devenu
load-bearing).

=== Modifié

* `vault create`, `set`, `delete`, `edit`, `rotation` — tous les
  chemins d'écriture passent par `Secrets::Recipients.encryption_keys`
  au lieu de la seule clé maîtresse. Pour un opérateur solo (pas de
  `recipients.toml`), le comportement est inchangé : la clé
  maîtresse seule est utilisée.
* `cli.cr` — nouveau dispatch + helpers privés pour le sous-arbre
  `recipients`.

=== Tests

* `spec/recipients_spec.cr` — 6 examples (add, rejet pour clés
  non-age1 / noms avec point / noms vides, multi-add, update au
  re-add, remove avec gestion du nom absent).
* `spec/vault_spec.cr` — 4 nouveaux examples pour le chemin
  multi-recipient (toute identité déchiffre, liste vide rejetée,
  recipients invalides au milieu d'une liste rejetés, overload
  string unique toujours fonctionnel).
* Total : 45 examples, 0 failures.

== v0.3.0 — 2026-05-10

=== Ajouté — cinq nouvelles sous-commandes (lot 1 de la roadmap README)

* `secrets delete -n VAULT -k KEY` (alias `rm`) — supprime une clé
  d'un coffre. Sortie 1 si la clé n'existe pas.
* `secrets edit -n VAULT` (alias `e`) — déchiffre le coffre dans un
  fichier temporaire mode 0600, lance `$EDITOR` (défaut `vi`),
  valide que le buffer édité reste un TOML correct, re-chiffre. Le
  fichier temporaire est wipé (best-effort) puis supprimé que
  l'éditeur ait réussi ou non. Si l'utilisateur quitte non-zéro, le
  coffre reste intact.
* `secrets rotation -n VAULT` (alias `r`) — re-chiffre le coffre
  avec la clé maîtresse courante. Utile si le fichier `.age` a
  fuité : un nouveau nonce donne un nouveau ciphertext pour le
  même plaintext, donc les anciennes copies ne peuvent plus être
  confondues avec l'état canonique. Prendra en compte le futur
  `recipients.toml` une fois la v0.4.0 multi-recipients livrée.
* `secrets diff -n VAULT --against PATH.age` (alias `df`) — compare
  le plaintext du coffre courant avec un autre fichier `.age`
  (typiquement un checkout git précédent). Les deux doivent
  déchiffrer avec la clé maîtresse courante. Sortie : diff unifié
  via `diff(1)`. Les deux buffers en clair passent par des
  tempfiles mode 0600, wipés + supprimés dans `ensure`.
* `secrets log -n VAULT` (alias `l`) — affiche le journal d'audit
  du coffre.

=== Ajouté — journal d'audit append-only par coffre

Nouveau module `Secrets::Audit` (`src/secrets/audit.cr`) qui expose :

* `Audit.log(vault, op, key=nil)` — append d'une ligne tab-separated
  `<RFC3339 UTC> \\t <user> \\t <op> \\t <key|->` dans
  `${XDG_CONFIG_HOME:-~/.config}/secrets/audit/<vault>.log`, mode 0600.
* `Audit.read(vault)` — retourne les lignes en tableau de strings.

`set`, `delete`, `vault create`, `edit` et `rotation` journalisent
toutes leurs mutations via ce module, donnant à l'opérateur un
historique « quand ai-je touché ce coffre la dernière fois, et
pourquoi ? ».

Le journal est append-only en esprit, pas inviolable — un attaquant
avec accès en écriture au fichier peut le falsifier. C'est un
audit côté opérateur, pas une frontière de sécurité.

=== Ajouté — helper `Secrets::Editor`

Nouveau module `src/secrets/editor.cr`. Lance `$EDITOR` (ou
`$VISUAL`, ou `vi`) sur un fichier temporaire mode 0600 et retourne
le buffer édité. Utilisé par `edit_cmd` mais conçu aussi pour le
verbe `secrets env` à venir (lot .env, v0.5.0). Wipe le fichier
temporaire dans `ensure` quelle que soit la sortie de l'éditeur.

=== Refactor

* `Secrets::XDG_CONFIG_HOME` et `Secrets::CONFIG_DIR` sont
  maintenant des constantes au top-level dans `src/secrets.cr`. Le
  CLI et le module audit s'y réfèrent tous deux.
* `cli.cr` gagne deux helpers privés : `parse_vault_only_args`
  (pour les commandes qui n'ont besoin que d'un nom de coffre) et
  `vault_path` (utilisé par edit, rotation, diff, et les
  read/write_vault existants).

=== Tests

* `spec/audit_spec.cr` — 4 examples couvrant la création du log,
  la sémantique d'append, le cas du coffre sans historique, et le
  mode 0600 du fichier.
* `spec/editor_spec.cr` — 4 examples couvrant l'édition réussie,
  le no-op, la sortie non-zéro de l'éditeur, et le nettoyage du
  fichier temporaire.
* Total : 31 examples, 0 failures.

== v0.2.6 — 2026-05-10

=== Modifié

Le repo avait été renommé `aloli-crystal/crystal-secrets` →
`aloli-crystal/secrets` en v0.2.2, mais l'ancien nom subsistait à
plusieurs endroits : 12 chaînes `crystal-secrets` en dur dans les
banners CLI, l'aide et les messages d'erreur ; le répertoire de
coffres par défaut `~/.config/crystal-secrets/vaults` ; et surtout
l'identifiant de service Keychain `dev.aloli.crystal-secrets`.
v0.2.6 termine le rename et embarque une migration transparente —
un utilisateur déjà initialisé ne voit rien.

* Banners, aide, messages d'erreur et la détection du binaire via
  `PROGRAM_NAME` passent tous de `crystal-secrets` à `secrets`.
* `DEFAULT_VAULT_DIR` est désormais
  `${XDG_CONFIG_HOME:-~/.config}/secrets/vaults` (avant :
  `crystal-secrets/vaults`). `XDG_CONFIG_HOME` est respecté
  (alignement sur `feedback_xdg_config_convention.md`).
* Identifiant du service Keychain : `dev.aloli.secrets` (avant :
  `dev.aloli.crystal-secrets`).

=== Migrations (transparentes, idempotentes)

* **Répertoire de coffres** — à chaque commande, si
  `~/.config/secrets/vaults` n'existe pas et que
  `~/.config/crystal-secrets/vaults` existe, ce dernier est renommé
  vers le premier. Le parent vide est supprimé.
* **Entrée Keychain** — `MasterKey.read` et `MasterKey.generate!`
  appellent d'abord `KeychainMacOS.migrate_legacy_if_needed!` : si
  le nouveau service-id n'a pas d'entrée mais l'ancien si, la
  valeur est copiée vers le nouveau, puis l'ancienne supprimée. Les
  deux opérations sont des no-op pour les installations déjà à jour.

Les deux migrations ne laissent aucune trace sur une installation
neuve ou chez les utilisateurs déjà passés en v0.2.5 sur les
nouveaux chemins/service.

=== Tests

* +4 specs couvrent la migration Keychain (no-op, copie, priorité
  quand les deux existent). Le faux script `security` a été étendu
  d'un mode stateful dans `spec/keychain_macos_spec.cr` pour pouvoir
  asserter des séquences de migration multi-étapes de bout en bout.
  Total : 23 examples, 0 failures.

== v0.1.0 — 2026-04-28

Première version publiée. macOS uniquement, mono-utilisateur,
recipient unique.

* Module **Diceware** (local) — génère des passphrases depuis
  deux wordlists embarquées : EFF Large (anglais, 7776 mots) et
  mbelivo 5d (français, 7776 mots). Trois modes de tirage :
  `:auto` (`Random::Secure`), `:manual` (l'appelant fournit ses
  dés), `:hybrid`. Sera remplacé par `aloli-crystal/diceware`
  quand celui-ci sera publié.
* **KeychainMacOS** — shell-out à `/usr/bin/security` pour
  `add-generic-password`, `find-generic-password`,
  `delete-generic-password`. Les valeurs secrètes sont passées
  via stdin, jamais argv.
* **Vault** — shell-out à `age(1)` pour
  chiffrement/déchiffrement single-recipient (ASCII armored).
  `openssl enc` (PBKDF2 600 000 itérations, AES-256-CBC, SHA-256)
  pour le papier de recovery par passphrase, parce que `age -p`
  exige un terminal interactif non simulable.
* **TomlCodec** — parse via `crystal-community/TOML.cr`,
  sérialiseur custom qui émet `KEY = "value"` et blocs
  `[section]`. Valeurs multi-lignes via littéraux `'''…'''`. La
  préservation des commentaires viendra avec
  `aloli-crystal/toml`.
* **MasterKey** — enrobe `age-keygen` pour générer la paire de
  clés age de l'opérateur, stocke la privée dans Keychain,
  retrouve la publique avec `age-keygen -y`.
* **Recovery** — `export(identity, passphrase) -> paper` et
  `import(paper, passphrase) -> identity` pour le scénario
  catastrophe où iCloud Keychain lui-même est indisponible.
* **CLI** — `init`, `vault create`, `get`, `set`, `list`,
  `master-key export/import`, `version`. Tous les flags long ont
  un short équivalent (convention Aloli).
* **50 tests** (Diceware 23, Keychain 8, Vault 6, TomlCodec 8,
  Recovery 5).
